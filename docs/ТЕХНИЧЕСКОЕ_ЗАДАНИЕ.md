# Техническое задание

## Проект
`Гравитация` — веб-платформа профессионального сообщества директоров школ Московской области.

Проект является закрытым клубом с доступом по приглашениям. Единый контекст продукта, масштаб и границы текущей реализации описаны в [`PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md).

## Статус документа
- Версия: `2.0`
- Дата актуализации: `16.07.2026`
- Тип документа: техническое задание / техническое описание текущей версии перед постоянным production-запуском

## 1. Назначение системы
Система предназначена для объединения директоров школ в единое цифровое пространство, в котором пользователь может:
- вести профиль директора и карточку школы;
- искать коллег и наставников;
- создавать мероприятия и записывать сотрудников;
- записываться на дополнительные активности;
- использовать встроенные уведомления и личные сообщения;
- отслеживать рейтинг активности;
- работать с административной панелью при наличии роли `admin`.

## 2. Целевая аудитория
- директора школ Московской области;
- потенциальные наставники внутри сообщества;
- администраторы платформы;
- представители министерства / кураторы проекта.

Регистрация не является открытой массовой регистрацией: целевая операционная модель — приглашение, заявка и проверка администратором. Обязательная техническая проверка invite-кода пока не является частью реализованного потока.

Ориентир масштаба — до 1500 зарегистрированных аккаунтов. Это не требование на 1500 одновременных сессий.

## 3. Технологический стек

### 3.1 Backend
- `Node.js 22.5+`
- `Express 4.x`
- `PostgreSQL 14+` через драйвер `pg`
- SQL-миграции с парными `up` / `down` файлами
- `Zod` для валидации
- `JWT + bcryptjs` для аутентификации
- `ws` для realtime-уведомлений
- `Helmet`, `CORS`, `cookie-parser`, `express-rate-limit`, `compression`, `morgan`

### 3.2 Frontend
- `HTML + CSS + Vanilla JavaScript (SPA)`
- модульная структура клиентских файлов без frontend-фреймворка;
- адаптивный интерфейс, inline SVG, service worker для push-уведомлений и переходов по ним; полноценный offline-кэш не заявляется.

### 3.3 Документация и качество
- `ESLint`
- `Prettier`
- `Vitest`
- `Supertest`
- GitHub Actions CI

## 4. Архитектурные принципы
- разделение backend на `routes` и `services`;
- разделение frontend на `app`, `views`, feature-модули (`profile`, `events`, `directors` и др.);
- использование миграций БД для эволюции схемы;
- production-safe конфигурация через централизованную валидацию env;
- structured logging и endpoints `health` / `ready`.

## 5. Основные модули системы

### 5.1 Аутентификация
Функции:
- регистрация;
- вход;
- выход;
- получение текущего пользователя;
- сброс пароля;
- защита от brute force через временную блокировку после серии неудачных входов.

Требования:
- JWT хранится в `httpOnly cookie`;
- в production reset token не возвращается в теле ответа;
- логин ограничен rate-limit и lockout-политикой.

Текущий путь допуска: регистрационная заявка получает статус после решения администратора. Если бизнес-процесс требует одноразовых invite-кодов, их выдача, срок действия и проверка должны быть добавлены отдельно.

### 5.2 Профиль директора
Функции:
- редактирование телефона, опыта, интересов;
- управление сильными сторонами и навыками;
- настройка статуса наставника;
- загрузка фото;
- отображение личного рейтинга и истории активности.

Требования:
- inline validation на клиенте;
- серверная валидация через Zod;
- данные профиля и связанных сущностей нормализованы.

### 5.3 Школа
Функции:
- редактирование названия, адреса, количества учащихся и педагогов;
- описание «могу быть полезен» и «хочу узнать»;
- переключение view/edit режима на клиенте.

### 5.4 Директора и наставники
Функции:
- список директоров с пагинацией;
- карточка директора;
- список наставников;
- полнотекстовый поиск;
- переход к отправке сообщения.

Требования:
- поиск должен использовать PostgreSQL full-text search и GIN-индекс;
- email скрывается для чужих пользователей и доступен только админу или владельцу.

### 5.5 Мероприятия
Функции:
- создание мероприятий;
- список мероприятий;
- регистрация сотрудников на мероприятие;
- soft delete мероприятий;
- уведомления при создании, регистрации и удалении.

### 5.6 Дополнительные активности
Категории:
- `Гравитация лидерства`;
- `Стажировка`;
- `Календарь`.

### 5.7 Сообщения
Функции:
- отправка личного сообщения;
- просмотр inbox в dropdown;
- unread badge;
- mark-all-read.

### 5.8 Уведомления
Функции:
- realtime через WebSocket;
- список уведомлений;
- badge непрочитанных;
- пометка прочитанным.

### 5.9 Администрирование
Функции:
- просмотр списка пользователей;
- аналитика по рейтингу и ролям;
- доступ только для `admin`.

- `seminar_materials`
- `announcements`

### 6.2 Особенности
- soft delete для мероприятий через `deleted_at`;
- нормализация strengths / skills / tags;
- полнотекстовый индекс директоров поддерживается при обновлении профиля, школы и регистрации;
- production использует PostgreSQL через обязательную переменную `DATABASE_URL`;
- тесты используют `pg-mem`, не создавая локальных файлов базы данных.

## 7. Безопасность
- CSP без `'unsafe-inline'` в `script-src`;
- CSRF-проверка для state-changing запросов;
- cookie-based auth с `httpOnly`;
- rate limit на API и auth;
- lockout после неудачных входов;
- валидация конфигурации на старте;
- structured logging для ошибок и событий сервера.

## 8. Нефункциональные требования
- сервер должен стартовать только при валидной конфигурации;
- все миграции применяются автоматически;
- `GET /health` используется как liveness-check;
- `GET /ready` используется как readiness-check;
- lint и тесты должны проходить без ошибок;
- проверки связности кнопок и API (`npm run check:buttons-db`), coverage и браузерные сценарии должны проходить;
- постоянная среда должна обеспечивать резервное копирование PostgreSQL и сохранность загружаемых файлов;
- система должна поддерживать дальнейший рост без возврата к монолитным route/frontend файлам.

## 9. Качество и сопровождение
- backend key domains вынесены в service-layer;
- frontend разбит на feature/view/app-модули;
- CI workflow проверяет форматирование, lint, API-тесты и браузерные сценарии;
- проект сопровождается актуальной Markdown-документацией.

## 10. Что считается готовым результатом
Результатом текущего этапа считается готовая к пилотному закрытому запуску foundation-версия системы, в которой:
- проходят тесты и lint;
- есть миграции и startup validation;
- реализованы основные пользовательские сценарии;
- архитектура допускает дальнейшее развитие без серьёзного роста технического долга.

Постоянный production-запуск дополнительно требует выбрать инфраструктуру вместо временного Render, подтвердить бэкапы и хранилище файлов, а также зафиксировать стратегию одной или нескольких копий приложения.
